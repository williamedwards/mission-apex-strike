# GravBoots (Unity 6000.5.9f1, URP)

Magnetic-boots 3D puzzle and obstacle course. Design and roadmap: `docs/PLAN.md`. Level sizes:
`docs/LEVEL_METRICS.md`.

- Game code: `Assets/_Project/Scripts/Runtime` (namespaces `GravBoots.*`, asmdef `GravBoots.Runtime`).
- The player motor works for any up direction: no `Vector3.up` in `Player/` except where world gravity is defined. Keep orientation math in pure static helpers (see `Gravity/SurfaceAlignment.cs`) with EditMode tests.
- Physics layers and tags live in `Layers.cs` (Player 8, Magnetic 9, tag `Lethal`). Magnetic surfaces = `Magnetic` layer + `Magnetic_Panel` material; the builder's `MagBox` makes them.
- `MagneticBoots` runs on `PlayerMotor.Stepped`, so stepping the motor drives the boots too. So does `PlayerSensor` (deaths, checkpoints, exit: an overlap check, not trigger messages); `LevelSession` owns start, respawn and the exit, and tests drive it with `Begin`/`Tick`. `LevelClock` ticks every `KinematicMover` before the motor (tests: `AutoSimulate = false`, `clock.Tick`), and the motor rides whatever its ground collider's transform does, so anything that moves a collider carries the player. `Hazards/Sentry` (and the older `Turret`) likewise expose `Tick` (`AutoSimulate = false` in tests); its hit test is geometric (`BeamMath`), not a physics query on the player.
- Design rule: the boots change orientation only along curves (`Level/CurvedRamp.cs`, the builder's `Curve`); sharp joins between magnetic surfaces are impassable by design. Don't add corner-transition logic.
- PlayMode tests step `PlayerMotor.Tick` by hand (`AutoSimulate = false`) at all 6 orientations. Add a case there for every movement promise.
- Run tests headless (Editor closed): `unity test . --mode EditMode --output Logs/test-EditMode.xml` (also `--mode PlayMode`).
- Real levels ("chambers") are hand-edited scenes in `Assets/_Project/Levels/`, built with the Level Kit (`Editor/LevelKit.cs`, window under GravBoots → Level Kit; guide in `docs/LEVEL_EDITING.md`). Never regenerate or overwrite them; edit them through the live Editor.
- The test bed scene and Player prefab are generated: menu **GravBoots → Build Camera Test Bed**, or headless with `unity run . -- -executeMethod GravBoots.Editor.TestBedBuilder.Build` (no `-quit`; the CLI adds it). Change the builder rather than hand-editing the generated scene.

## Driving the open Editor (Pipeline package)
- Command names are `<group> <name>` as two words, e.g. `unity command editor set_auto_tick`, `unity command script eval '<C#>'`, `unity command console get -- --level error --tail 20`, `unity command runtime simulate_key -- --key W --action down`. Put command parameters after `--`. Check names with `unity command <group>` (for example `editor`, `editor.playmode`, `capture`, `console`, `script`, `runtime`).
- If every main-thread command times out, look for a modal dialog in the Editor (`xdotool search --pid <pid>` lists window titles). The Editor's main loop doesn't run while a modal is open.
- Don't hand-edit `.unity`/`.prefab` YAML while an Editor is reachable.
- With the Editor open, run tests through it: `unity command test run -- --mode editor` works synchronously, but PlayMode needs `--mode playmode --async_tests true`, then poll `unity command test status` (results land in `Temp/pipeline_test_status.json`, with keys `FullName`/`Status`/`Message`). The runner can leave an `Assets/InitTestScene*.unity` behind; delete it.
- An unfocused Editor runs at roughly 10–20 fps, which makes per-frame camera measurements unreliable; prefer deterministic tests. Simulated key presses (`--action press`) sometimes get lost, so hold keys down and up instead. The first `script eval` after entering Play mode can be slow.
